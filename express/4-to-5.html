Express 4 to 5 upgrade: what broke, verbatim errors, and fixes

Versions tested: express 4.22.3 upgraded to express 5.3.0, on 21 October 2026 (UTC), on Linux with Node v22.22.0 and npm 10.9.4. Method: a real 430-line Express 4 app was run on both versions under a test harness, and every failure was recorded as it happened: boot crashes, thrown errors, compiler errors and 1,915 HTTP responses, each checked to come from the intended Express version and process. These findings are observed, not summarised: none comes from the Express changelog or migration guide, which were deliberately not read, and anything that was not observed is marked untested.

Summary: moderately painful, and mostly silent. The app won't start until five route strings are rewritten, and about a dozen other changes return wrong results with no error, most of them with no 4.x deprecation warning either. Bringing the app back to identical behaviour took 17 fixes and 60 changed lines; each fix is one line, and finding them is the work. The four most-downloaded companion packages install and run, but the cors README's own examples crash Express 5, and @types/express stays on 4.x, passing code that crashes at boot.

Machine-readable copy: /express/4-to-5.json holds the same 50 findings in the same order, as a JSON array. Each finding has id, title, severity (silent: wrong behaviour and no error; loud: throws or fails to compile; cosmetic: header-only difference), error_message (verbatim, or null), symptom, cause, fix_before, fix_after and evidence (observed or documented). Each id is also the finding's anchor on this page. For exact string matching use the JSON, because this page's source escapes < and &.

Report by @Arjun, 21 October 2026.

Find affected code first

Express 5 reports only one bad route pattern per start. In the test app these two commands found all five route strings and all three req.query writes, with no false positives. Route paths built from variables or arrays will not match; check those by hand. Run them from the project root:

# route strings Express 5 rejects or reads differently
grep -rnE "\.(get|post|put|patch|delete|del|all|use|options|head|route)\(['\"][^'\"]*[*?()]" --include='*.js' --include='*.ts' --exclude-dir=node_modules .

# writes to req.query
grep -rnE "req\.query(\.[A-Za-z_\$][A-Za-z0-9_\$]*|\[[^]]*\])?\s*=[^=]" --include='*.js' --include='*.ts' --exclude-dir=node_modules .

Findings, most severe first

Order: security issues first, then silent changes (no error, so they ship unnoticed), then loud errors (at startup, per request, then at compile time), then header-only changes. Every finding in this report was observed by running code. In each finding the verbatim error_message comes first, with fix_before and fix_after directly below it.

1. Security: auth guard rewritten as '/admin/*splat' lets GET /admin/ through without a token

id
admin-wildcard-guard-bypass
severity
silent
evidence
observed
error_message
null
fix_before
// Express 4 original, which crashes 5.x at boot: app.all('/admin/*', guard);
app.all('/admin/*splat', guard);
fix_after
app.use('/admin', guard); // preferred: also covers /admin
// or the exact 4.x meaning:
app.all('/admin/{*splat}', guard);
symptom
On 5.3.0, app.all('/admin/*splat', guard) does not run the guard for GET /admin/: the request returns 200 with the admin page and no token. On 4.22.3 the original app.all('/admin/*', guard) returned 401. Paths with at least one character after /admin/, such as /admin/stats, still match, so only the bare /admin/ is exposed. No error and nothing in the log.
cause
'/admin/*' crashes 5.x at boot (wildcard-route-boot-crash), and '/admin/*splat' is the obvious rewrite. In 5.x a named wildcard without braces needs at least one character, so '/admin/*splat' misses /admin/ and '/*splat' misses /. In a 13-URL matrix, 4.x X/* matched exactly what 5.x X/{*name} matches. 4.22.3 printed no deprecation warning for the original pattern.

2. Security: Express 5 route syntax deployed onto Express 4 never matches, so guarded routes are served without a token

id
v5-route-syntax-on-express-4
severity
silent
evidence
observed
error_message
null
fix_before
// Routes rewritten for 5.x, but package-lock.json or the deployed image still has express 4.x
app.all('/admin/{*splat}', guard);
fix_after
// Ship the route rewrite and `npm install express@5` in the same commit,
// and log the running version at boot:

symptom
Code rewritten for 5.x but running on 4.22.3 (an old lockfile, a stale image): '/admin/{*splat}' never matches, so GET /admin/stats is served without a token. No error or warning on 4.22.3. The same code works as written on 5.3.0.

4.22.3 accepts the 5.x pattern string without complaint, and the pattern matches no request. The two route syntaxes do not mix: old patterns crash 5.x, and new ones silently mis-match on 4.x.

3. Security: req.query = clean(req.query) is silently ignored, so query sanitizers stop sanitizing

id
req-query-reassign-ignored
severity
silent
evidence
observed
error_message
null
fix_before
app.use((req, res, next) => {
  req.query = clean(req.query);
  next();
});
fix_after
// Pin one writable copy before anything writes to req.query (also runs on 4.x)
app.use((req, res, next) => {
  Object.defineProperty(req, 'query', { value: req.query, writable: true, configurable: true, enumerable: true });
  next();
});
app.use((req, res, next) => {
  req.query = clean(req.query);
  next();
});
symptom
On 5.3.0, in plain JavaScript (not strict mode), a sanitizer that reassigns req.query has no effect: $where reaches the handler. On 4.22.3 it was stripped. No error and nothing in the log. In strict-mode code the same line throws instead (req-query-reassign-strict-mode).
cause
In 5.x req.query is a getter with no setter that re-parses the URL on every read (req.query === req.query is false), so the assignment is dropped. 4.22.3 printed no warning. Untested: express-mongo-sanitize and hpp reassign req.query, so they are likely affected.

5. Defaults written onto req.query are lost, so pagination breaks and limits stop being enforced

id
req-query-writes-lost
severity
silent
evidence
observed
error_message
null
fix_before
app.use('/api/users', (req, res, next) => {
  req.query.page = parseInt(req.query.page, 10) || 1;
  req.query.limit = Math.min(parseInt(req.query.limit, 10) || 20, 100);
  next();
});
fix_after
// Pin one writable copy first (also runs on 4.x); the middleware above then works unchanged.
// Or keep your values off req.query.
app.use((req, res, next) => {
  Object.defineProperty(req, 'query', { value: req.query, writable: true, configurable: true, enumerable: true });
  next();
});
symptom
On 5.3.0, with middleware that sets pagination defaults on req.query: GET /api/users returned {"total":3,"users":[]} instead of page 1 with 3 users, ?limit=1&page=2 returned 2 users instead of 1, and ?limit=500 was not clamped to 100. No error.
cause
In 5.x every read of req.query re-parses the URL (req.query === req.query is false), so values written onto it are gone by the next read. 4.22.3 printed no warning.

6. app.listen on a busy port prints "listening" and exits 0 instead of crashing

id
listen-error-swallowed
severity
silent
evidence
observed
error_message
null
fix_before
app.listen(PORT, () => console.log(`Acme listening on http://localhost:${PORT}`));
fix_after
app.listen(PORT, (err) => {
  if (err) throw err;
  console.log(`Acme listening on http://localhost:${PORT}`);
});
symptom
On 5.3.0, with the port already taken, the app printed Acme listening on http://localhost:4300 and exited with code 0. With another open handle (a DB pool, a timer) it keeps running and serves nothing, while the old process keeps answering. On 4.22.3 it crashed with Error: listen EADDRINUSE: address already in use 0.0.0.0:4300 and exit code 1.
cause
In 5.x the app.listen callback runs even when listening failed, with the error as its first argument; a callback that ignores its argument hides the failure. 4.22.3 printed no warning.

Recommended upgrade order

Do everything except the route rewrites on 4.x first. Then bump Express, bump @types/express and rewrite the routes in one commit, because the two route syntaxes do not mix.

  1. On 4.x, clear every deprecation warning. Run the whole test suite with stderr visible and fix each express deprecated and body-parser deprecated line. A warning appears only when its line runs, so coverage matters. Every fix applied for them ran on 4.22.3; the clearCookie maxAge one was left alone, since 5.x ignores that option.
  2. Still on 4.x, ship the fixes that work on both versions. All of these ran on 4.22.3:
    • app.set('query parser', 'extended') if any client sends bracket queries (bracket-query-not-parsed)
    • stop writing to req.query, or add the writable-copy shim (req-query-writes-lost)
    • default req.body to {} after the parsers (req-body-undefined)
    • app.listen(PORT, (err) => { if (err) throw err; … }) (listen-error-swallowed)
    • { root } on every res.sendFile and res.download (sendfile-dot-folder-404)
    • a dedicated /.well-known static mount (well-known-not-served)
    • res.redirect(req.get('Referrer') || '/') instead of 'back' (redirect-back-literal)
    • express.urlencoded({ extended: true }) wherever the options are missing (urlencoded-default-not-extended)
    • router.param validation instead of an inline (regex) in a path (inline-regex-boot-crash)
    • app.use(cors()) instead of app.options('*', cors()) (cors-readme-options-star)
  3. List every route string and req.query write before the bump, with the two commands in Find affected code first. Startup reports only one bad pattern per boot. Paths built from variables or arrays won't match; check those by hand.
  4. In one commit, bump and rewrite together. Run npm install express@5 and npm install -D @types/express@5. Rewrite X/* to X/{*name} and :x? to {/:x}, and read wildcard captures as arrays (.join('/')). Old patterns crash 5.x, and new ones silently mis-match on 4.x.
  5. Boot until it starts, then fix the types. Each start names one PathError; search the code for its originalPath. Then fix the tsc errors, which now find the removed APIs.
  6. Test the silent cases on purpose. Send a trailing-slash request to each guard (/admin/), bracket queries, pagination defaults and a POST with no body. Fetch /.well-known/*, walk any redirect('back') flow, download from the real deploy path, and start on a busy port. Diff response headers if tests or clients compare them exactly.
  7. Deploy, then confirm what is running. Log require('express/package.json').version at boot and make sure the old process is gone. On 5.x a second server on a busy port prints "listening" and exits 0 while the old one keeps answering.

  • Likely breakers, untested (hypotheses from the probes): express-async-errors patches express/lib/router/layer, which no longer exists. express-list-endpoints reads app._router. express-mongo-sanitize and hpp reassign req.query, which throws in strict mode. @opentelemetry/instrumentation-express patches router internals, and @apollo/server has a separate @as-integrations/express5 package.
  • Download counts came from the registry search API's downloads.weekly (npm's own index, dated 2026-10-16 to 10-20), because the test environment's network policy blocked api.npmjs.org. They were not cross-checked against the official downloads API.
  • The express command name (the CLI from express-generator) was not checked for collisions.
  • Older companion versions: only the latest of each was tested. A project pinned to an older major that declares express ^4 could hit ERESOLVE; not tested.
  • One environment: Linux, Node 22.22.0 and npm 10.9.4. Not tested: Node 18 or 20 (Express 5 declares node >= 18), Windows, macOS, pnpm, yarn or Docker. Whether pnpm's node_modules/.pnpm store path trips the dot-directory sendFile change is a hypothesis.
  • App shape: CommonJS only. Strict-mode behaviour was shown with TypeScript output and strict functions, not a real ESM app. NODE_ENV=production was never set. There was no HTTP/2, TLS, real reverse proxy, database, session store, upload handling or auth library.
  • Inferences, not observations: that ACME (Let's Encrypt) HTTP-01 challenges under /.well-known/ would fail; that dropping (\\d+) sends paths like /users/search into an id handler; that the header changes break clients or exact-header tests.
  • The release notes were deliberately not read, so which of these findings the Express 5 changelog or migration guide already documents is unknown.
  • TypeScript: only TypeScript 7.0.2 and only @types/express. Other @types/* packages that depend on it were not checked for version conflicts.
  • The four companions ran in small test apps that load the upgraded project's installed packages; they were not wired into the main app.
  • The harness: every check passed on 4.x first, and full header and body diffs caught what checks didn't assert, but code paths the app doesn't have are untested. Requests went one at a time, with no load or performance comparison.
  • The evidence: the harness, experiment scripts and raw results existed only in the temporary workspace used for the run; nothing was committed to a shared repository.
