jsPDF 3 to 4 upgrade: what broke, verbatim errors, and fixes

Versions tested: jspdf 3.0.4 upgraded to jspdf 4.2.1, on 22 October 2026 (UTC), on Linux with Node v22.22.0 and npm 10.9.4, and in headless Chromium 141. Method: a real 175-line jsPDF 3 app, which writes 6 PDFs (17 pages) with text and fonts, images, a jspdf-autotable table, mixed page sizes and .html(), was run on both versions in Node and in the browser, and every failure was recorded as it happened. Because a PDF can generate without error and still be wrong, every PDF was also compared across versions: bytes, structure, embedded fonts, images, extracted text and rendered pixels. Small probe scripts then tested the areas that a diff of the two versions' built code showed had changed, and older add-on versions were installed to test npm ci. Every run first checked that the intended jsPDF version was the one running. These findings are observed, not summarised: none comes from the jsPDF release notes or changelog, which were deliberately not read, and anything that was not observed is marked untested.

Summary: close to painless for browser code, and for any code that hands jsPDF its fonts and images as data: every baseline PDF came out byte-identical to 3.0.4, covering text, custom fonts, images, autotable tables, multi-page layouts and .html(). The pain is in Node code that passes file paths: addImage(path) now throws, addFont(path) silently saves the PDF without the font, and neither of the two remedies the error message names works as written. addMetadata() now XML-escapes its input, which silently changes XMP and PDF/A metadata, and projects still on jspdf-autotable < 5.0.7 or svg2pdf.js < 2.7.0 pass npm install locally but fail npm ci. Go straight to 4.2.1: npm audit flags jspdf <=4.2.0, 3.0.4 included, as critical.

Machine-readable copy: /jspdf/3-to-4.json holds the same 12 findings in the same order, as a JSON array. Each finding has id, title, severity (silent: wrong output and nothing thrown, though jsPDF may log to the console; loud: throws, fails to compile or fails to install; cosmetic: the PDF bytes change and nothing breaks), error_message (verbatim, or null), symptom, cause, fix_before, fix_after and evidence (observed or documented). Each id is also the finding's anchor on this page. For exact string matching use the JSON, because this page's source escapes < and &.

1. addFont() with a file path in Node saves the PDF without the font, and nothing is thrown

id
add-font-file-path-not-embedded
severity

evidence

error_message
jsPDF PubSub Error Trying to read a file from local file system. To enable this feature either run node with the --permission and --allow-fs-read flags or set the jsPDF.allowFsRead property.
jsPDF PubSub Error Cannot read properties of undefined (reading 'widths')
fix_before
doc.addFont('assets/DejaVuSans-Bold.ttf', 'DejaVu', 'bold');
fix_after
// works on 3.x and 4.x; the output is byte-identical to 3.0.4
doc.addFileToVFS('DejaVuSans-Bold.ttf', fs.readFileSync('assets/DejaVuSans-Bold.ttf').toString('base64'));
doc.addFont('DejaVuSans-Bold.ttf', 'DejaVu', 'bold');
symptom
On 4.2.1, in Node, doc.addFont(path, …) throws nothing. jsPDF logs two errors to console.error (their first lines are above), and doc.save() still writes the PDF, without the font: pdffonts lists it under its file path as a Type 1 font with emb no, viewers substitute another face (poppler drew a condensed one), ✓ drops out of the extracted text, and the file shrank from 287,901 to 149,987 bytes. On 3.0.4 the same call embedded the font. No exception reaches your code; the console is the only signal.
cause
In Node, 4.2.1 refuses to read local files unless you opt in, so the font file is never read (the same block as add-image-file-path-throws). addFont reports the failure through jsPDF's internal PubSub, which logs it instead of throwing.

2. addMetadata() now XML-escapes its input, so text escaped in advance, as the 3.x JSDoc asked, is escaped twice

id
add-metadata-double-escaped
severity
silent
evidence
observed
error_message
null
fix_before
doc.addMetadata('Tom &amp; Jerry'); // escaped in advance, as the 3.x JSDoc asked
fix_after
// 4.x only: change it in the upgrade commit (on 3.0.4 this string gives XMP that won't parse)
doc.addMetadata('Tom & Jerry');
symptom
On 4.2.1, doc.addMetadata('Tom &amp; Jerry &lt;Q3&gt; report') stores the XMP value Tom &amp; Jerry &lt;Q3&gt; report, with the entities as literal text. On 3.0.4 the value was Tom & Jerry <Q3> report. The pages render the same. No error.
cause
4.x XML-escapes the string passed to addMetadata(); 3.x inserted it as it was, which is why its JSDoc asked for escaped input. Plain text gives valid XMP on 4.2.1 (the value reads Tom & Jerry), but on 3.0.4 the same plain string gives XMP that an XML parser rejects (ExpatError: not well-formed (invalid token)), so the change has to ship with the upgrade.

3. addMetadata() with XMP markup stores it as escaped text, so the PDF/A identification (pdfaid:part) disappears

symptom
On 4.2.1 the XMP holds 0 pdfaid:part elements instead of 1: the markup is stored as escaped text, so the file no longer identifies itself as PDF/A. No error.

4.x escapes everything passed to addMetadata() (add-metadata-double-escaped); markup goes through only in the new raw mode, addMetadata(xmp, true), which takes a complete x:xmpmeta packet. On 3.0.4 the same call nests the packet inside jsPDF's own wrapper with xmlns:jspdf="true" and gives 2 x:xmpmeta elements, so make this change in the upgrade commit, not before.

4.x escapes ( and ) in the JavaScript string it writes. 3.x wrote them as they were, so an unbalanced ) ended the PDF string early.

Recommended upgrade order

Make the file-path, AcroForm and add-on changes on 3.x first, because they work on both versions. Then bump jspdf straight to 4.2.1 and make the 4.x-only changes in the same commit.

  1. Still on 3.x, make the changes that leave the output identical. Each of these was verified byte-identical on 3.0.4:
    • replace every addImage, addFont and loadFile call that passes a file path with the file's bytes (fs.readFileSync), using the VFS for fonts (add-font-file-path-not-embedded, add-image-file-path-throws)
    • rename AcroForm option and value names that contain spaces (acroform-names-with-spaces)
  2. Still on 3.x, bump the add-ons: npm install jspdf-autotable@^5.0.7 svg2pdf.js@^2.7.0. Both still declare jspdf 3 support and ran correctly with 3.0.4 (npm-ci-eresolve-old-addons).
  3. Upgrade straight to 4.2.1, not 4.0.0 to 4.2.0. npm audit flags jspdf <=4.2.0 as critical (GHSA-f8cm-6447-x5h2, local file inclusion and path traversal), and reports 0 vulnerabilities for 4.2.1. In the same commit, make the 4.x-only changes:
    • pass plain text to addMetadata, or a complete XMP packet with true (add-metadata-double-escaped, add-metadata-xmp-markup-becomes-text)
    • if you kept file paths, set jsPDF.API.allowFsRead to the folder's real path, with as any in TypeScript (allow-fs-read-symlink-rejected, ts-allow-fs-read-not-typed)
  4. Verify: npm ci passes, no jsPDF PubSub Error appears in the logs, pdffonts shows emb yes for every custom font, and the XMP is right if you depend on PDF/A.
  5. Don't turn on node --permission just for jsPDF (node-permission-flag-breaks-save). If you do, you also need --allow-fs-write and --allow-child-process.

No change observed

Once file paths were replaced with bytes, all 6 baseline PDFs and the 4 companion-tool PDFs were byte-identical between 3.0.4 and 4.2.1, after removing the creation date, the file ID, /Producer (which names the jsPDF version) and the cross-reference table. That covers:

  • standard fonts in 7 styles, a TTF loaded through the VFS with non-Latin text, getTextWidth, splitTextToSize, alignment, justification and maxWidth, rotation, links and setProperties
  • images: an RGBA PNG from bytes, a palette PNG with transparency from a data URL, a JPEG from raw base64 with rotation, alias reuse with 'FAST' compression, and getImageProperties
  • jspdf-autotable: a 7-page table with hooks, a footer, compress: true and lastAutoTable.finalY
  • mixed page sizes, setPage, internal.getNumberOfPages() and internal links
  • in the browser: .html() from an element and from a string, the doc.save() download, output('dataurlnewwindow'), and addImage(url) and addFont(url)
  • TypeScript: the 4.2.1 types only add declarations, and typical calls compile the same way

Not verified

Everything ran on one machine, with one Node version, one package manager, one browser engine and one PDF renderer.

  • Viewers: rendering was checked only with poppler. Adobe Acrobat and Reader, Chrome's PDF viewer, Firefox's pdf.js, macOS Preview and mobile viewers were not tested, and each substitutes fonts (add-font-file-path-not-embedded) and draws form appearances (acroform-names-with-spaces) its own way.
  • Browsers: only headless Chromium 141. Firefox, Safari/WebKit and mobile browsers were not tested, and html2canvas output depends on the engine.
  • Module systems: only Node CommonJS require and the browser UMD bundle. Not run: the ES build (jspdf.es.min.js) that webpack, Vite, Rollup and esbuild use, Node ESM import, SSR frameworks, Deno, Bun, Electron and web workers. The ES build's code was not diffed either.
  • Node versions: only Node 22. The file-read block checks process.permission, which is experimental on Node 20 and absent on Node 18, so its behaviour there is unknown.
  • Operating systems: Linux only. Windows paths in allowFsRead (backslashes, drive letters, case-insensitive matching) were not tested, and the macOS /tmp to /private/tmp case is inferred from the Linux symlink test.
  • Package managers: only npm 10.9.4. How pnpm and yarn handle the add-on peer mismatch was not tested, and npm ls exiting 0 despite the mismatch was seen on npm 10 only.
  • TypeScript: only TypeScript 6.0.2 with --strict and --skipLibCheck.
  • Features never triggered: encryption and passwords; FreeText annotations; images larger than 512 MB; output('pdfobjectnewwindow') and output('pdfjsnewwindow'); asynchronous loadFile(url, false, cb) and loadImageFile; outlines and bookmarks, right-to-left text, setLanguage, and .html() with fontFaces or remote (CORS) images; GIF, BMP and WebP images; AcroForm text fields and list boxes; CJK, Arabic and emoji fonts; output('blob') and output('bloburl') in Node.
  • Seen in the 4.x code but never triggered (documented, not observed, so not listed as findings): the PNG, GIF and BMP decoders now throw Image dimensions exceed 512MB, which is too large. for very large images. A FreeText annotation's /DS string now goes through the encryptor, which matters only with encryption on. output('pdfobjectnewwindow') and output('pdfjsnewwindow') were rewritten to use DOM calls; the filename is now URI-encoded, and & is used when pdfJsUrl already contains ?. The package exports map gained a "default" condition, so resolvers that match neither node nor browser now get the ES build instead of failing. loadImageFile is an alias of loadFile, so it hits the same file-read block.
  • PDF/A was checked only by counting pdfaid elements in the XMP; no veraPDF validation.
  • The security advisory was only seen to clear in npm audit. No path-traversal inputs were tried, so whether 4.2.1 actually fixes it was not verified.
  • Old lockfiles: a lockfile with dompurify older than 3.3.1 would presumably be bumped by the upgrade. That is inferred from the range change, not reproduced.
  • Performance: no speed or memory comparison.
  • Other wrappers: jsPDF wrappers beyond the four companions, such as html2pdf.js, were not tested.
  • Download counts for the four companions are the figures given when the test was set up; they were not re-checked.
  • Method limits: comparisons ignored the creation date, file ID, /Producer and the cross-reference table. Renders were compared at 60 dpi with a per-channel threshold of 24, so smaller pixel differences in files that were not byte-identical would not be flagged. Probes were chosen from the baseline plus a diff of the Node and UMD builds, so changes elsewhere, or in code paths that were not probed, would be missed. Each .html() PDF has 1 poppler error on both versions; it was not investigated.
  • The evidence: the app, probe scripts, PDFs and comparison output existed only in the temporary workspace used for the run; nothing was committed to a shared repository.
